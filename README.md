## DOD 방식과 OOP 방식으로 각각 구현된 컴포넌트 시스템의 성능 벤치마킹


[FPS 서버 프로젝트](https://github.com/whitefish2n2/few_pow_sign_dedicated)를 진행하며 컴포넌트 시스템을 구현해야 했습니다. 처음에는 유니티의 구현대로 따라 구현했는데, 해당 구현 방식에 힙 할당/해제 비용, 포인터 체이싱 및 캐시 미스, 단편화 문제 등이 발생할 수 있다는 것을 알고 유니티의 트렌드인 DOD의 좋은 부분을 적용하여 이 문제를 해결하였습니다. 해당 프로젝트는 이런 전환으로 어느 정도의 성능 향상을 이끌어 낼 수 있었는지 확인하기 위한 실험입니다. 테스트 코드는 Google Gemini가 기존 코드를 기반으로 작성하였습니다.

---

## 기존 사용했던 Unity-Like 방식
OOP와 유니티의 구현방식을 따라 GameObject가 여러 종류의 Component를 동적으로 소유하는 구조입니다.

메모리 구조: 컴포넌트 객체들이 힙 메모리 공간에 무작위로 산개되어 할당됩니다.

동작 방식: 업데이트 루프 시 Array -> GameObject 포인터 -> Component 포인터 -> vTable을 거쳐 실행됩니다.

성능적 한계: 컴포넌트의 부착/해제 설계는 유연하지만, 필연적인 포인터 체이싱으로 인해 심각한 캐시 미스와 분기 예측 실패가 누적됩니다.

## [FPS 서버 프로젝트](https://github.com/whitefish2n2/few_pow_sign_dedicated) 에서 사용했던 방식(DOD 방식)
데이터 지향 디자인을 바탕으로 OOP의 가상화 및 상속을 이용할 수 있게 구현되었습니다.

메모리 구조: 한 종류의 컴포넌트 객체들이 하나의 Array 안에 저장되게 합니다.

동작 방식: 업데이트 루프 시 특정 타입만이 저장되어있는 Array를 순회하며 각 타입에 대해 Update를 실행합니다.

## 결과
| | OOP (Unity-Like) | DOD |
|---|:---:|:---:|
| 평균 실행 시간 | 5299.33 ms | 2343.31 ms |
| 성능 변동률 | 0.74% | 0.36% |
| 표준 편차 | ±40.17 ms | ±9.02 ms |
| 성능 차이 | - | **2.26배** |

DOD 방식은 평균 **2.26**배의 성능 향상폭과 OOP의 표준편차 ±40.17 ms에 비해 **±9.02 ms**의 안정적인 성능을 보였습니다.
(10회 테스트, 테스트 환경 Windows 11 i9-14900HX 32GB DDR4 RAM)
