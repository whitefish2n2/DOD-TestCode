## 기존 사용했던 Unity-Like 방식
OOP와 유니티의 구현방식을 따라 GameObject가 여러 종류의 Component를 동적으로 소유하는 구조입니다.

메모리 구조: 컴포넌트 객체들이 힙 메모리 공간에 무작위로 산개되어 할당됩니다.

동작 방식: 업데이트 루프 시 Array -> GameObject 포인터 -> Component 포인터 -> vTable을 거쳐 실행됩니다.

성능적 한계: 컴포넌트의 부착/해제 설계는 유연하지만, 필연적인 포인터 체이싱으로 인해 심각한 캐시 미스와 분기 예측 실패가 누적됩니다.

## Few-Pow-Sign-Dedicated 방식(DOD 방식)
데이터 지향 디자인을 바탕으로 OOP의 가상화 및 상속을 이용할 수 있게 구현되었습니다.

메모리 구조: 한 종류의 컴포넌트 객체들이 하나의 Array 안에 저장되게 합니다.

동작 방식: 업데이트 루프 시 특정 타입만이 저장되어있는 Array를 순회하며 각 타입에 대해 Update를 실행합니다.


---

와 같은 방식으로 구현되었고, DOD 방식은 평균 2.24365배, 124.37%의 성능 향상폭과 OOP의 퍼센트 변동률 0.74%에 비해 0.36%의 안정적인 퍼센트 변동률을 보였습니다.
(10회 테스트, 테스트 환경 Windows 11 i9-14900HX 32GB DDR4 RAM)

테스트 코드는 Google Gemini가 기존 코드를 기반으로 작성하였습니다.
